CP to 게임 원격 설정화 — 개발 요청서

크로스프로모션 팝업의 to 게임·순서·이미지를 클라 빌드 없이 시트에서 바꾸기 · 2026-08-25 · 대상 = 마종 / 코지타일즈 / 코인매치 / 퍼즐블록마스터 / 솔시티저니(신규 구현)

REQUEST
  1. CP 팝업이 어느 게임으로 보내는지를 원격 JSON에서 읽도록 바꿔 주세요. 지금은 앱 ID가 클라에 하드코딩돼 있어 게임 하나 추가에 전 게임 빌드가 필요합니다.
  2. 바꿀 곳은 5군데입니다 — ① 게임별 프리팹 → 공용 프리팹 1개 ② 앱ID Map → JSON 조회 ③ 번들 이미지 → CDN 원격 로드 ④ enum → key_number ⑤ 세션 캡·로테이션을 게임별 설정으로. 다섯이 한 세트입니다.
  3. 이 작업 뒤부터 게임 추가·순서 변경·국가 변경은 전부 시트만으로 됩니다. 빌드 없음. 9/1 CP 개편에 함께 적용합니다(개발 8/21~8/28 · 검수 ~8/31).
  4. 시트 쪽은 이미 적용해 뒀습니다. 다만 §6의 필드명 5건이 시트에 이미 반영돼 있어, JSON 재배포는 클라의 신·구 이름 겸용 처리 뒤에 해야 합니다.
1. 지금 왜 빌드가 필요한가 퍼즐블록마스터 클라 기준 · 기존 CP 4개 게임이 같은 구조 (솔시티저니는 CP 미구현 — §5)
빌드를 묶는 요소현재 코드왜 문제인가
① 게임별 프리팹 ViewCreator.ts:447
showCPCount % 2 === 1 → "PopupSolitaireCityJourney" / "PopupMahjong" 프리팹을 이름으로 로드		 to 게임 1종 = 프리팹 1개. 게임을 늘리려면 프리팹을 만들어 번들에 넣어야 하므로 무조건 빌드
② 앱ID 하드코딩 PopupCrossPromotion.ts
targetGames: Map<CrossPromotionType, string> 9개 앱ID		 to 게임이 코드 상수. 앱ID 하나 바꾸려도 빌드
③ 번들 이미지 @property([cc.SpriteFrame]) randomCPFrame — 프리팹에 스프라이트로 박힘 배너 교체 = 빌드. 이미지를 CDN에 올려도 이것 때문에 빌드가 남습니다
④ enum → key_number @property({type: cc.Enum(CrossPromotionType)}) target enum에 없는 게임은 지정 자체가 불가. 게임별로 enum도 제각각 (PuzzleMaster vs PuzzleBlockMaster, 코인매치엔 CoinMatch 자체가 없음)
정작 랜딩 함수 자체는 제약이 없습니다
Fbi.switchApp(appID, payload, targetGame) → FBInstant.switchGameAsync(appID, payload). 목적지가 앱 ID 문자열 하나로 끝납니다. 게임이 늘어도 분기가 늘지 않습니다. 즉 위 4가지는 전부 데이터를 코드에 넣어둔 탓이지 구조적 제약이 아닙니다.
2. 바꿔 주실 것 4개 게임 클라 공통 · 한 번만 하면 이후 영구히 시트 운영
항목변경 내용
1 공용 프리팹 1개로 통합 게임별 프리팹(PopupSolitaireCityJourney·PopupMahjong…) → PopupCrossPromotion 1개. ViewCreator.showPopupCrossPromotion()은 프리팹 이름을 고르는 대신 이번 회차에 노출할 key_number를 골라 팝업에 넘깁니다.
2 앱ID를 JSON에서 조회 targetGames Map 제거 → cp_{게임명}.json의 games에서 이름 → key_number 조회.
onClickPlay()는 Fbi.switchApp(cfg.app_id, {social, player_id}, cfg.log_name)로 그대로 호출.
3 이미지 원격 로드 randomCPFrame 배열 제거 → routes의 버전으로 만든 URL을 cc.assetManager.loadRemote로 받아 changeSprite에 세팅. 기존 changePromotionImage()의 인덱스 순환 로직은 불필요해지므로 삭제(이미지가 게임별 1장으로 고정됨).
4 enum → 문자열 키 @property target: CrossPromotionType → target: number(key_number). CrossPromotionType enum과 게임별 이름 불일치는 이 시점에 전부 사라집니다. 정본은 아래 §4 마스터 탭의 key_number.
5 세션 캡을 게임별로 현재 DataManager._showCPCount 단일 카운터가 캡 판정과 로테이션을 겸하고 있습니다(Fbi.ts:694 캡 3 / ViewCreator.ts:447 %2). 게임별 카운터 Map<gameKey, count>로 분리하고, 캡 상수 3 → country_data.cp_cap_per_game를 읽게 해 주세요. 로테이션은 %2 고정 대신 cp_order 배열 길이로 순환합니다(idx % order.length) — 1종·2종·3종이 분기 없이 처리됩니다.
⑤는 나머지와 분리 개발이 안 됩니다
캡 카운터와 로테이션이 같은 변수 하나라, 순서를 JSON에서 읽게 바꾸는 순간 캡 판정도 같이 손봐야 합니다. ①~⑤를 한 세트로 봐 주세요.
3. JSON 스키마 파일 2종 — from 게임별 CP 파일(신규) + 국가별 설정(기존 파일 확장)

① cp_{게임명}.json 신규 — from 게임마다 1개. 그 게임에 필요한 것만 들어갑니다.
위치 제안: {CDN}/cp/cp_{게임명}.json — 예: /cp/cp_coin_match.json

// cp_coin_match.json — 시트 cp_game_master + cp_image 에서 생성
{
  "games":  { "Mahjong": 1, "CozyTiles": 2, "CoinMatch": 3,
              "PuzzleBlockMaster": 4, "SolitaireCityJourney": 5, "ThePuzzle": 6 },
  "routes": { "2": 1, "5": 1, "1": 1 }     // 키 = to 게임의 key_number · 값 = 배너 버전
}

// cp_the_puzzle.json — 같은 games, routes만 다름
{
  "games":  { ... },
  "routes": { "5": 1, "2": 1, "4": 1 }
}
게임별로 자기 파일만 받으면 됩니다
games는 이름 ↔ 번호 대응표라 전 게임 공통이고, routes에는 그 게임이 쓰는 조합만 들어갑니다. 앱ID는 games의 번호로 country_data 쪽과 맞춰 읽습니다.
노출 순서는 routes가 아니라 country_data가 정합니다
routes는 버전표지 순서가 아닙니다(JSON 객체라 순서 보장이 없습니다). 어느 게임을 몇 번째로 보여줄지는 country_data의 cp_order 배열이고, routes는 그 조합의 배너가 몇 번째 버전인지만 알려 줍니다.
배너 파일명 — {CDN}/cp/image/{from 게임명}_{to 게임명}_{version}.png
예 — 마종에서 보여주는 코지타일즈 배너 = /cp/image/Mahjong_CozyTiles_1.png
version이 캐시 대응입니다. 배너를 갈아끼울 때 시트에서 숫자를 +1 하면 파일명이 바뀌어 CDN 무효화 없이도 새 그림이 내려갑니다.
routes에 없는 조합이면 그 순번을 건너뛰어 주세요(§7).

② country_data/{게임명}.json 기존 확장 — 국가별 순서·캡. 게임마다 기존 파일에 4개 필드만 추가.
예: https://d26ml67612e64s.cloudfront.net/block_blast/data/country_data.json

{
  "US": {
    "cross_it": 0, "cross_it_limit": 0, "show_cross": 1, ...  // 기존 필드 그대로
    "cp_order": [2, 5, 1],       // key_number 배열 · 순환 순서
                              // [2, 5] → 2종 교대 / [2] → 1종 고정 / [] 또는 없음 → CP 미노출
    "cp_cap_per_game": 3          // 게임 1종당 세션 최대 노출
  }
}
CP 신규 필드는 지금 배포해도 안전합니다
DataManager.updateCountryData()가 {...defaultCountryData, ...countryData}로 병합하므로, 현재 클라는 모르는 키를 그냥 무시합니다. CP 신규 필드(cp_order·cp_cap_per_game)만 보면 시트를 먼저 내보내도 됩니다. 단 §6 필드명 변경은 별개이니 그쪽 조건을 먼저 확인해 주세요. 단 CountryData 인터페이스에는 4개 필드를 optional로 추가해 주세요.
4. 시트 구조 적용 완료 [통합] country_data 시트 · 기획 쪽에서 운영
탭 3종의 역할 — 시트 readme 탭에도 같은 내용을 적어 뒀습니다
cp_game_master — 신규 게임을 추가하거나, 특정 게임을 CP 대상에서 켜고 끌 때
cp_image — CP 배너 이미지 버전 관리
country_data_(게임명) — 나라별 설정 + 그 게임의 CP 순서(cp_order_1~3)와 세션당 노출 횟수(cp_cap_per_game)
탭내용
cp_game_master 신규 key_number · log_name · game_name · app_id · in_use · note — cp_{게임명}.json의 games 소스. 여기에 행을 추가하면 전 국가 탭 드롭다운에 자동 반영됩니다. 옆의 order_choices는 드롭다운 선택지(0 + key_number)를 만드는 수식 열입니다
cp_image 신규 from · to · version · in_use · note — cp_{게임명}.json의 routes 소스. 한 행 = 배너 한 장. 행은 손으로 만들지 않습니다 — 국가 탭에서 순서를 정하고 메뉴에서 순서 → 배너 목록 동기화를 누르면 필요한 조합이 자동으로 생기고, 순서에서 빠진 조합은 status가 '순서에 없음'으로 바뀝니다(지우지는 않음). image_preview는 만들어질 파일명을 보여주는 수식 열입니다
country_data_mahjong · country_data_cozy_tiles · country_data_coin_match · country_data_puzzle_block_master · country_data_solitaire_city_journey 이름 변경 한글 탭명을 country_data_ + 소문자 게임명으로 변경. 탭명 = 출력 JSON 파일명 = 스크립트 FROM_KEY_BY_SHEET 키이므로 셋은 항상 같이 바꿉니다. 스키마는 공통 10개 + 게임 고유 + CP 4개로 맞췄습니다 — 고유 필드가 달라 탭마다 컬럼 수가 다릅니다(12~17열).
국가는 19개국으로 통일했고, 실제 사용 여부는 in_use 열로 켜고 끕니다
README기존 사용설명서 탭. 생성 로그가 남는 곳이라 JSON으로 만들지 않습니다
식별자는 3층으로 나눠 씁니다 — 이름이 바뀌어도 아무것도 안 깨지게
칸쓰이는 곳변경 가능성
key_number시트 cp_order_1~3 · JSON cp_order · 클라 조회불변 · 번호 재사용 금지(지운 게임 번호를 다른 게임에 다시 쓰지 않음)
log_nameBQ 로그값(logCrossPromotionPopup·logBtnCrossPromotionPlay) · 이미지 파일명사용=1 이후 불변 · 바꾸면 그 시점 앞뒤 로그가 다른 게임처럼 쪼개짐
game_name시트 가독용(한글). JSON에 안 나감자유 — 게임 이름이 바뀌면 여기만 고칩니다
게임 리브랜딩이 나면 game_name만 바뀝니다. key_number·log_name은 그대로라 클라·국가 탭·기존 BQ 쿼리가 전부 무사합니다. 미출시 2종(마종슬라이드·머지스토리)은 in_use=0이라 로그가 아직 없으므로 켜기 전까진 log_name도 자유롭게 바꿔도 됩니다.

1행 = 컬럼 설명 / 2행 = 헤더 / 3행부터 데이터 · 기존 규칙 그대로. 현재 등록값: 마종 = 코지타일즈·솔시티저니·퍼즐블록마스터 / 코지타일즈 = 솔시티저니·코인매치·더퍼즐 / 코인매치·퍼즐블록마스터 = 코지타일즈·솔시티저니·마종.

탭별 스키마 — 다수결로 통일, 단독 사용은 고유 유지
5개 클라를 전수 조사해 3종 이상이 읽는 필드는 공통으로 올리고, 1종만 쓰는 필드는 그 게임에만 뒀습니다.

이로 인해 생기는 클라 작업은 §5 게임별 목록에 반영했습니다.

5. 게임별 작업 목록 담당자별로 나눠 보실 수 있게 게임 단위로 정리했습니다 · ①~⑤는 §2 공통 항목
먼저 — 5개 게임 공통 (§2)
① 공용 프리팹 1개로 통합 · ② 앱ID를 cp_{게임명}.json에서 조회 · ③ 배너 이미지 원격 로드 · ④ enum → key_number(number) · ⑤ 세션 캡을 게임별 카운터로 분리. 아래는 그 위에 게임별로 추가되는 것만 적었습니다.

권장 — 필드를 하나씩 고치지 마시고 받을 때 한 번 정규화해 주세요
JSON을 받는 지점에서 키의 대소문자와 언더바를 지운 형태로 한 번 색인해 두면, 클라의 CountryData 인터페이스도 참조부도 지금 이름 그대로 두면 됩니다. IapPopup → iap_popup 처럼 구분자가 달라진 것까지 한 번에 흡수됩니다. 
// updateCountryData() 등 JSON을 받는 지점에서 한 번만
const norm = {};
for (const k in json) norm[k.toLowerCase().replace(/_/g, '')] = json[k];

// 읽을 때 — 기존 이름을 그대로 넘겨도 찾아집니다
const pick = (name) => norm[name.toLowerCase().replace(/_/g, '')];
pick('Cross_IT')  // → cross_it
pick('IapPopup')  // → iap_popup
이 방식이면 배포 순서 제약이 없습니다
옛 이름 JSON과 새 이름 JSON을 둘 다 읽게 되므로, 클라 빌드와 JSON 배포 중 어느 쪽이 먼저 나가도 안전합니다.
정규화를 안 넣으실 경우에만 아래 순서를 지켜야 합니다 — ① 클라에서 필드명을 새 이름으로 교체 → ② 빌드 배포 → ③ JSON 생성·업로드. ②와 ③ 사이에는 새 클라가 옛 이름 JSON을 읽는 구간이 생깁니다.
어긋나면 조용히 틀립니다
JSON 키 이름이 곧 클라가 읽는 이름입니다. 어긋나면 에러 없이 undefined가 되어 클라 하드코딩 기본값으로 떨어집니다. 로그에도 안 남고 화면도 멀쩡해서, 지표가 변한 뒤에야 알게 됩니다.

통일 규칙 — 전부 소문자 snake_case 한 가지. 약어도 소문자로 내립니다(cross_it · rv_fail_cross · context_type_nru · cp_order_1). 밸런스 시트(key_number · in_use)와 같은 표기라, 앞으로 시트가 달라도 규칙은 하나입니다. 탭 이름은 바꾸지 않았습니다 — 탭명 = 출력 파일명 = 로그값이라 Mahjong·CozyTiles 그대로입니다.

9. 서버 · 인프라 쪽 할 일 게임 서버 로직 변경은 없습니다 — CDN 배포와 캐시가 전부
항목내용
CDN 캐시 무효화 이게 제일 중요합니다. 현재 country_data.json은 고정 URL로 로드하고 캐시 버스터가 없습니다 (Intro.ts:421 → CCres.loadJsonAssetRemote). 시트를 고치고 JSON을 올려도 CloudFront·브라우저 캐시가 남아 있으면 반영이 안 됩니다. 배포 시 invalidation을 걸거나 TTL을 짧게 잡아 주세요. 지금도 같은 제약이지만, 앞으로 운영 빈도가 올라가므로 정책을 정해야 합니다
CDN 폴더 구조 from 게임마다 CP 파일이 1개씩 생깁니다. 아래 구조로 잡으면 됩니다 —
cp/cp_{게임명}.json · cp/image/{from}_{to}_{version}.png · country_data/{게임명}.json
Drive → CDN 업로드 파이프라인에 cp/ 경로 추가 필요
CP 배너 이미지 호스팅 원격 로드로 바뀌므로 CORS 허용 + Content-Type 확인. 같은 파일명으로 이미지를 교체하면 캐시 때문에 안 바뀝니다 — 교체 시 invalidation 또는 파일명 버전 규칙 필요
출력 파일명 변경탭명을 영문화해 마종.json → Mahjong.json으로 바뀝니다. CDN 업로드 경로 매핑을 같이 고쳐야 합니다
BQ 로그 정의서 CP 로그값에 새 게임명(log_name)이 추가됩니다. 정의서·enum 문서 갱신 — 코드 변경은 아님
Meta 앱 설정 확인 필요 신규 게임 앱ID가 switchGameAsync 대상이 되는지(같은 비즈니스·앱 그룹 조건) 확인. 기존 9개는 이미 동작하지만 신규 2종은 미확인 — Alex 확인 항목
게임 서버는 손댈 게 없습니다
CP 설정은 전부 정적 JSON이고 서버 API를 타지 않습니다. 위 항목은 전부 배포·캐시·문서이지 서버 로직이 아닙니다.
