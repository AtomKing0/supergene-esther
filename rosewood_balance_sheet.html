개발자가 읽는 순서

이 문서는 어떤 값을 읽어 어떻게 계산하는지 설명한다. 화면 동작·저장·통신·실패 처리는 개발 기획서에서 확인한다. 각 표는 기능 설명 → 처리 규칙 → 컬럼 설명 순으로 읽는다.

예를 들어 오더는 order_rule로 발급 조건을 확인하고, order_item·order_slot_band로 후보를 뽑고, order_item_count로 요구 개수를 정한다. 보상은 order_price × 수량의 합으로 계산한다. 생성 결과와 난수·순번·타이머는 클라이언트가 함께 저장한다.

첫 리뷰 준비본. 기본 오더 5슬롯과 공유 발급 예산을 반영했다. 일부 보상·운영 정책, 번역·사운드에는 확정할 항목이 남아 있다. 문장 정리 완료와 출시 밸런스 검증 완료는 구분한다. 구현 준비 상태와 원작 비교

1. 시트 공통 사용법

표와 JSON의 관계

시트 한 탭이 클라이언트 JSON 파일 하나에 대응한다. Row1은 사람이 읽는 설명, Row2는 JSON 필드 이름, Row3부터는 데이터다. 헤더 없는 빈 열을 기준으로 왼쪽은 클라이언트 데이터, 오른쪽은 기획 검수용 설명이다.

이름과 식별 번호

새 필드 이름은 소문자와 언더바를 사용한다. 기존 호환 형식의 필드명은 각 표의 실제 스키마를 따른다. 문구 키의 값은 T_STRING_CODE 형식이며 string_code의 식별 컬럼은 Key다. 일반 표의 key_number = band × 10000 + 순번은 최초 발급 뒤 유지한다. 행을 정렬하거나 삭제해도 기존 번호를 당기거나 재사용하지 않는다.

단위와 빈 값

시간은 기본적으로 초(_sec)다. 진동 길이처럼 명시된 _ms는 밀리초다. 금액·개수·기간은 각 컬럼의 단위를 따른다. none·0은 각 필드에 정의된 의미로 사용한다. 0을 모두 미정·무제한·꺼짐으로 처리하면 안 된다. 미확정 필드는 설명에 별도로 표시한다.

확률과 가중치 계산

  • 확률: 10000이 100%다. 예: 2500은 25%.
  • 정규화 가중치: 같은 그룹의 합을 10000으로 맞춘다. 후보 일부를 제외했다면 남은 가중치 합으로 나눠 추첨한다.
  • 생산 내용물 가중치: 각 아이템이 남아 있는 개수다. 나온 항목의 개수를 1 줄이고 모두 소진하면 초기 구성으로 채운다. 합을 10000으로 바꾸지 않는다.

참조·보상·활성 상태

다른 표를 참조하는 키는 실제 대상 행이 있어야 한다. 보상은 아이템 키와 수량을 한 쌍으로 읽고 값이 있는 쌍을 모두 처리한다. in_use가 있는 표는 활성 행만 사용한다. 이 컬럼이 없는 호환 표는 각 표의 설명을 따른다.

수정 후 확인

기획자가 시트를 수정하면 변경분을 클라이언트 JSON과 문서에 반영한다. 키·참조·단위·가중치·보상 누락을 검사한 뒤 배포한다. 보상·진행 속도를 바꾼 경우에는 같은 플레이 조건으로 수급과 소요 시간을 다시 확인한다. 데이터 검사 통과만으로 플레이 밸런스가 검증된 것은 아니다.

1-12. 시트가 실수를 막는 장치

FK 칸을 하늘색으로 칠하는 것만으로는 오타가 막히지 않는다. 적재 스크립트가 시트에 직접 드롭다운과 주석을 건다.

장치범위하는 일
엄격 드롭다운63칸불리언은 체크박스, 보상 칸과 FK 는 목록 밖 값을 막는다. 짧은 enum 은 경고만 띄운다. 값이 전부 다른 식별자 칸에는 걸지 않는다
헤더 셀 주석335칸Row2 셀에 그 칸의 뜻·규칙·타입·근거가 주석으로 붙는다. 내용은 _schema.json 에서 그대로 태우므로 손으로 다시 적지 않는다
Row1 A열에 표 이름45탭PMM_{테이블명} 을 적는다. 탭을 복사해도 A1 이 원본 표를 말해 준다

1-13. 보상은 이렇게 적는다

보상 칸에는 접두형 문자열 키 한 개만 넣는다. 「종류」 칸을 따로 두지 않는다 — 접두가 곧 종류다.

  • 보상 칸의 값은 언제나 currency_gem · item_2501 같은 접두형 키 하나다. 접두를 보면 재화인지 아이템인지 바로 읽힌다.
  • 열 이름도 여덟 탭이 같다 — reward_item_key 하나다.
  • 범주 칸(reward_type)을 따로 두면 한 열에 범주와 값이 섞인다. 그래서 두지 않는다.
규칙내용
1보상 칸의 값은 reward_key.reward_key 의 접두형 문자열 키뿐이다 — currency_*(7) · booster_*(2) · item_*(238) · 빈 슬롯 "none". 정수 아이템 코드를 보상 칸에 넣지 않는다
2열 이름은 reward_item_key(단일) · reward_item_key_N(다중)과 짝인 reward_amount · reward_amount_N 하나뿐이다. 예외 하나 — product 는 reward_type 이라는 이름을 쓴다. 담기는 값은 위 규칙과 똑같다
3「종류」 칸을 따로 두지 않는다. 접두가 곧 종류다
4보드 아이템 그래프(item_spec.item_code · produce_item_N · generator_N)는 정수 그대로다. 클라가 쓰는 아이템 id 이고 보상 이름공간과 다른 축이다. 두 이름공간을 잇는 자리는 reward_key.item_code 한 칸뿐이다
5시즌 패스 토큰 적립량은 보상 슬롯이 아니다. token_amount 라는 다른 이름을 쓴다

검사는 이름 규칙으로 전 표를 훑어 988칸을 reward_key 에 대조한다(빌드가 센다). reward_item_key 라는 이름을 쓰면 저절로 검사에 든다. 시트에서는 reward_key 250행짜리 엄격 드롭다운이 목록 밖 값을 막는다.

1-14. 비슷해 보이는 값의 주인

이름이 닮은 칸이 여럿 있다. 주인이 어느 표인지를 여기서 정한다. 같은 숫자를 두 곳에 적지 않는다.

1-15. 무엇이 얼마나 나오는지 보여 준다

생성기와 상자를 누르면 무엇이 얼마나 나오는지를 상세 팝업에 적는다. 다만 확률 컬럼은 만들지 않는다 — 표시할 값은 개수에서 계산한다.

1-17. 젬이 모자랄 때 — 상점으로 보내는 길

젬을 치르는 실행을 눌렀는데 잔액이 모자라면 그 자리에서 부족분을 적은 판을 띄우고 상점 젬 진열대로 보낸다. 상한도 쿨다운도 없다 — 모자랄 때마다 매번 뜬다. 원작이 그렇고, 우리도 같게 간다.

한 번 도는 길

실행을 누른다  →  잔액 < 가격 인가  →  결제 모듈이 켜져 있는가  →  바로 상점으로 보내는 스위치가 켜져 있는가  →  판(부족분 · [상점으로] · [닫기])  →  젬 진열대  →  닫으면 원래 창으로 되돌린다

부족분   = 가격 − 보유 젬        ← 판에 적는 숫자
추천 팩  = 없음                   ← 진열대 맨 위로 스크롤만 한다
노출 가능 = 언제나 참              ← 상한 · 쿨다운 · 억제가 전부 0
  • 추천 팩을 고르지 않는다. 「부족분 이상인 가장 싼 팩」 같은 규칙을 두지 않는다 — 원작에 그런 규칙이 없다. 젬 진열대로 보내고 고르는 것은 유저에게 맡긴다.
  • 사고 돌아와도 실행을 대신 눌러 주지 않는다. 되돌아온 화면에서 다시 누른다.
  • 레벨 2 이하면 상점이 젬 진열대만 보인다(const.shop_gem_only_max_level) — 처음 떨어진 유저에게 살 것을 좁힌다.
  • 스위치 feature_toggle.gem_lack_jump_to_shop 를 켜면 판을 건너뛰고 곧장 상점으로 보낸다. 도착지는 같다.

1. 기능과 처리 규칙

이 표로 개발할 기능

보드 아이템의 합치기·생산·판매 규칙

  • item_code로 행을 찾는다. 합치기는 merged_item_code, 판매는 selling_price, 생산은 spread_*와 produce_*를 읽는다. 오더 코인 보상은 order_item의 order_price를 사용한다.

처리·저장 규칙

생산 전 재고·빈 보드 칸·에너지를 모두 검사한다. 성공한 생산만 재고와 에너지를 차감하고 결과·타이머를 함께 저장한다. 생산 내용물의 남은 개수는 아이템 종류별로 공유하고, 재고·회복 타이머는 보드의 생성기 개체마다 따로 저장한다.

계산 상세: 생성기에서 리소스가 정해진 개수만큼 나온다

아래 순서와 수식을 적용한다.

한 바퀴
한 바퀴 = Σ produce_weight_N            (그 생성기가 내놓는 총 개수)
첫 탭   = produce_weight_i / 한 바퀴
탭할 때마다  나온 것이 1 줄어든다        (남은 것이 줄면 확률이 움직인다)

  • 한 바퀴 10000 으로 맞추면 이 개수가 바뀌어 나오는 순서가 통째로 달라진다
  • 어디에 붙는가 아이템 종류마다 하나다. 같은 생성기를 둘 놓아도 남은 개수를 나눠 쓴다

처리·저장 규칙

유형별 발급 예산과 빈 슬롯 채우기

슬롯 수와 카드당 요구 수를 분리하고 유형별 대기를 공유한다.

기본 슬롯: 1·2 normal / 3 high / 4 random_3 / 5 random_4. 연속 특수 오더는 별도 6번.

④ 예산이 0이면 대기 중인지 확인한다. 대기 중이 아니면 next_refill_at=현재 시각+refresh_sec를 저장한다. 카드 생성은 하지 않는다.

2. 후보 아이템의 추첨 비중 계산하기

현재 클라이언트 표를 기준으로 계산한다.

계산 가중치 = 보드 상황 배수
반복 제한 대상이고 제수 > 0이면: 최종 가중치 = 계산 가중치 ÷ 제수
그 외: 최종 가중치 = 계산 가중치
각 후보가 뽑힐 확률 = 그 후보의 최종 가중치 ÷ 전체 후보의 최종 가중치 합

계산 예: 보드 상황 배수가 10000이면 계산 가중치는 10000다.
제수가 100인 상황을 가정하면 최종 가중치는 100.0다. 다른 후보의 최종 가중치도 같으면 두 후보의 확률은 각각 50%다.
배수는 확률 자체가 아니다. 모든 후보의 최종 가중치 합으로 나눈 뒤에 확률이 정해진다.

  • 후보 사용 여부: order_item.in_use가 참인 아이템만 사용한다. 후보마다 같은 기본값을 곱할 필요 없이 보드 상황 배수의 상대 비중으로 계산한다.
  • 보드 상황 배수: 다른 오더가 이 체인을 요구하고 보드 아이템으로 납품 가능하면 100배. 아무 오더도 요구하지 않으면 1000배. 아무 오더도 요구하지 않고 보드에 후보와 같거나 더 낮은 단계 아이템이 있으면 10000배. 다른 오더가 요구하지만 아직 납품할 수 없으면 기본 배수 1을 쓴다. 조건별 배수는 하나만 적용하며 중복 곱하지 않는다.
  • 배수를 읽을 곳: const의 order_weight_mult_required_enough, order_weight_mult_not_required, order_weight_mult_higher_level.
  • 제수: order_item.repeat_weight_decrease. 0이면 나누지 않는다. 제한 횟수는 const.order_repeat_reset_count를 읽는다. 체인별로 모든 랜덤 슬롯이 같은 카운터를 공유한다. 자세한 갱신 순서는 오더 납품 페이지에 있다.

현재 클라이언트 표를 기준으로 계산한다.

코인 보상 = Σ(order_item.order_price × 요구 개수)
일반·고정 오더 난이도 = Σ(order_item.diff_score × 요구 개수)
오더 경험치 보상 = 없음

  • diff_score: 아이템별 난이도 점수다. 난이도 기준의 이벤트 점수 계산에 참조할 수 있으며 코인으로 지급하지 않는다. 현재 오더 단계 범위는 종류와 레벨만 사용한다.

1. 기능과 처리 규칙

이 표로 개발할 기능

오더 완료 시 이벤트별로 얻는 점수

  • 현재 활성 이벤트마다 별도로 score_base를 확인한다. coin이면 오더 코인, diff이면 오더 난이도를 기준값으로 쓴다.

처리·저장 규칙

score_min 오름차순에서 기준값 이상 조건을 만족한 마지막 행을 사용한다. 정확히 경계에 도달하면 새 행을 쓴다. 해당 행이 없거나 기준값이 0이면 지급하지 않는다. score_max는 구간 설명·검사용이며 행 선택은 score_min으로 한다. token_pct > 0이면 floor(기준값 × token_pct / 10000), 아니면 token_fix다. 이벤트마다 결과를 별도로 지급한다.

5. 활성 이벤트마다 점수 계산하기

현재 클라이언트 표를 기준으로 계산한다.

① 활성 이벤트의 event_order_score 행을 찾는다.
② score_base가 coin이면 코인 보상, 난이도 기준이면 난이도 합을 사용한다.
③ score_min 오름차순으로 정렬한 뒤 기준값 ≥ score_min인 마지막 행을 선택한다. 해당 행이 없거나 기준값이 0이면 지급하지 않는다.
④ token_pct > 0이면 점수 = floor(기준값 × token_pct ÷ 10000).
   비율이 0이면 점수 = token_fix. 두 값이 0이면 지급 점수도 0.
⑤ 다른 활성 이벤트에도 같은 절차를 각각 적용한다.

현재 오더 러시 비율은 2500(=25%)다. 코인 20인 오더를 완료하면 floor(20 × 2500 ÷ 10000) = 5점을 얻는다.
같은 비율을 사용하는 봇 레이스가 동시에 켜져 있다면 그 이벤트에도 별도로 같은 점수를 지급한다.

  • floor: 소수점 이하는 버린다. 5.5는 5가 된다.
  • 시즌 패스·주간 태스크: 오더 완료 횟수 목표는 1건당 +1이다. 이 점수 환산식과 구분한다.
  • 구간 경계: 원작과 같이 score_min으로 행을 선택한다. 경계와 같으면 새 행을 사용한다. score_max는 범위 설명·데이터 검사용이며 런타임 선택에는 쓰지 않는다. 같은 이벤트의 score_min 중복은 데이터 오류다.

1. 기능과 처리 규칙

이 표로 개발할 기능

원작 방식의 주간 누적 목표

  • 같은 타입 행동을 현재·미래·과거 일차의 모든 미달성 행에 가산한다. target_val에서 멈추고 자정에 초기화하지 않는다. week_day는 수령 개방 일차다.

처리·저장 규칙

개방된 달성 행의 [받기]에서만 토큰과 보상을 한 번 지급한다. 지난 목표는 종료 전까지 수령한다. 종료 때 달성·미수령 행을 회수한다. 원작 보상 미연결 행은 빈 보상으로 실행하지 않는다.

기간과 일차

회차 시작~종료는 [start_at,end_at). 시작부터 24시간마다 일차를 연다. 현재 일차 = min(7, floor((now-start_at)/86400)+1). 월요일·UTC 자정은 우리 편성값일 뿐 원작 고정 요일로 주장하지 않는다.

누적

회차 시작 이후 발생한 동일 타입 행동을 모든 일차의 미달성 목표에 반영한다. progress = min(target_val, progress+delta). 미래 일차도 쌓이고 자정에 초기화하지 않는다. 접속 카운터만 실제 접속한 일차에 한 번 +1이다.

결석과 무료 완주

참조안은 전체 1135토큰, 실결제 목표 80토큰을 제외하면 1055로 마지막 구간과 같다. 7일 접속 중 하루를 놓치면 누적 로그인7 목표의 30토큰을 못 얻어 무료 경로는 최대1025가 된다. 지난 행동 목표는 만회할 수 있지만 로그인 결석까지 복구되는 것은 아니다.

목표 수령

조건 달성은 지급이 아니다. week_day ≤ 현재 일차이고 progress ≥ target_val이며 claimed=false일 때 [받기]를 제공한다. 수령 시 토큰과 행 보상을 한 번 지급한다. 이전 일차 목표도 종료 전까지 달성·수령한다.

마일스톤

목표 수령으로 old_token < token_required ≤ new_token을 통과한 모든 구간의 묶음 보상을 자동 지급한다. 별도 마일스톤 [받기]를 만들지 않는다. 그림을 누르면 보상 설명만 연다. 같은 reward_group·milestone의 모든 reward_slot 행을 묶어 한 번 지급한다.

종료 정산

회차 데이터를 지우기 전에 달성·미수령 목표를 한 번 회수하고, 그 토큰으로 넘은 구간도 지급한다. 미달성 목표만 소멸한다. 정산 스냅샷과 recovered 표시를 보존해 재접속·재시도로 중복 지급하지 않는다.

주간 별

별 사용 회차의 최종 묶음에서 별 1개를 얻고 회차를 넘어 보존한다. 최대 3개이며 3개가 되면 별 보상 묶음(원작 8항목)을 한 번 자동 지급한다. 별 보상 수령 완료 시 다음 회차 시작에서 별을 초기화한다.

별 손실과 보너스

원작은 회차 중 본체를 한 번 연 참여자에 한해 종료 별 상태를 정한다. 정산 후에도 이번 회차 별을 못 얻었으면 기존 별에서 1개 차감(최소 0). 별 보상 완료 뒤에는 bonus_star_enabled=1이면 다음 회차 본체 최초 진입 때 1개로 시작하고, 0이면 0개로 시작한다. 단순 연속 접속 보너스가 아니다.

저장과 지급

클라이언트가 일차·진행·UI를 계산하고 회차 상태를 로컬 저장한다. 결제·재화 등은 확정된 행동 이벤트만 반영한다. 서버는 저장 동기화와 수령 멱등성을 확인하며 별도 일일 목표 생성기를 두지 않는다.

난도 선택

원작 서버에 난도별 표가 있으면 저장 난도(없으면 초기 난도)로 목표·보상 세트를 각각 선택하고 각 표의 최대 난도로 상한을 제한한다. 회차 동안 고정한다. 완료율은 수령 토큰과 달성·미수령 토큰을 합쳐 최종 요구량으로 나눈다. 0.53 미만은 태그0, 1 이상은 태그2, 나머지는 태그1이다. 직전 태그와 이번 태그가 0·0이면 난도−1(최소1), 2·2이면 +1(최대4). 조정한 태그는 10 또는12로 저장하고 최근3개를 보존해 매주 연속 조정되지 않게 한다. 복귀 유저 회차 데이터 제거 시에는 실패 태그0을 사용한다. 난도표가 없는 참조안에는 이 분기를 켜지 않는다.

집계 이벤트 연결

coin→gold, good_review→smile, event_token→deco, spend_gem→gem, iap→pay로 원작 TaskEventType에 대응한다. card·card_4star·card_5star·order·merge·login은 같은 코드다. 이 프로필의 event_token은 꾸미기 토큰 획득량이며 이벤트마다 다른 재화를 임의 합산하지 않는다. 마일스톤 보상을 지급하는 동안 주간 행동 집계는 잠시 중단한다(원작 StopCalcProgress/StartCalcProgress).

시트 적용

profile_id·config_version·회차 시작/종료·bonus_star_enabled를 회차 시작 때 고정한다. 중간 설정 변경으로 이미 진행한 목표를 교체하지 않는다. 이벤트 토큰 대상·도구 허용 목록·카드/리뷰 기능·보상 매핑을 포함한 설정이 완전해야 회차를 활성화한다.

  • 예외: D≤0, 감소하는 누적 점수, 0 시드는 데이터 오류다. 시드·곡선·참가 시각을 복원하기 전에는 무작위 점수 표시를 시작하지 않는다.

이 표로 개발할 기능

사용자 행동에 연결할 진동

  • 행동에 맞는 패턴·duration_ms·priority를 읽는다. 진동이 꺼져 있으면 실행하지 않는다.

처리·저장 규칙

진동 길이의 단위는 밀리초다. 한 프레임에 여러 요청이 겹치면 priority가 작은 하나만 실행한다. 사용자 입력으로 발생한 동작에만 붙인다. 운영체제 지원 여부와 실제 패턴 느낌은 기기에서 확인한다.

출처와 스키마 참고

값 출처 rosewood_dev_spec.html 사운드 · 진동 페이지

데이터 형식 예외 7열이다. 패턴 다섯 가운데 하나를 고르고 지속 시간을 함께 든다.

스키마 참고 진동 피드백의 진실원이다. 패턴은 다섯뿐이고 새 패턴을 만들지 않는다 — tap 성공 · double 한 건 완료 · pulse 상태 변화 · staccato 막힘 · burst 큰 성취. duration_ms 는 설계값이고 실기에서 조정한다. 설정의 진동 토글이 꺼져 있으면 이 표 전체가 돌지 않는다. priority 는 같은 프레임에 둘이 겹쳤을 때 작은 쪽만 울리는 순서다.
