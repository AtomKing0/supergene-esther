PROTO-001 스토리 연출 채팅 영상 내부 테스트 2026. 8. 14.

채팅 vs 영상, 같은 스토리로 붙여보기

스토리 전달 방식을 채팅 화면과 영상 화면 중 무엇으로 갈지 결정하기 위한 3퀘스트 분량 프로토타입 사양입니다. 빌드는 두 벌로 나누되 스토리 데이터는 한 벌만 공유합니다.

① 작업 목록 프로토 빌드까지 남은 액션

파트항목내용세부
클라채팅 빌드story_node + story_dialogue 2개만. task 노드에서 머지보드 진입.데이터 →
클라영상 빌드story_node + present_video 2개만. dialogue 노드는 씬 클립 재생으로 대체.데이터 →
아트영상 클립 4개 · 55초vo_<scene_id>.mp4. 제작 방식(스틸컷 이어붙이기 / 풀스크린) 먼저 결정. 씬별 목표 길이는 duration_target_sec에 있습니다.두 가지 안 →
아트표정 16장<speaker>_<emotion> 이름으로 전달하면 데이터는 수정 없이 그대로 붙습니다.규격 →
아트챕터 브릿지 영상RYUL 제작. 우리 인물로 B(풀스크린 애니메이션) 형태. 세 안 공통이라 먼저 진행 가능합니다.규격 →
아트스틸컷 2장 선택still_<내용>.png. 채팅 빌드용. 생략 가능하지만 정확한 비교를 위해선 권장 — 영상은 클립에 녹여서 나갑니다.플로우 →
기획설문 준비6문항. 인원 절반은 채팅 먼저, 절반은 영상 먼저 배정.문항 →

② 회의 정리 결정된 것과 갈린 것

아젠다 1 — 게임 코어 재미 검증, 스토리 진행 방식

안방식제작 경로
A원작 게임의 채팅 형식 스토리 진행 말풍선 렌더러 직접 구현
B스틸컷 프리뷰 형식 스토리 진행 VN builder 활용
C영상 형식 스토리 진행 VN builder 활용
  • 공통 — 챕터 브릿지 역할의 영상은 세 안 모두에 동일하게 삽입합니다. (ryul 제작)
  • 데이터는 세 안이 같습니다. A는 story_dialogue까지 읽고, B·C는 story_node + present_video만 읽습니다 → ③ 설계 원칙.

아젠다 2 — 챕터 브릿지 영상 제작 방식

안방식
aryul이 원래 제작하던 방식 그대로
bVN builder를 활용해 제작

브릿지 영상은 세 안 공통이라 아젠다 1의 선택과 무관하게 먼저 진행할 수 있습니다. 다만 b로 가면 B·C와 제작 파이프라인이 하나로 합쳐집니다.

③ 설계 원칙 빌드는 두 벌, 콘텐츠는 한 벌

  • 채팅 전용 빌드와 영상 전용 빌드를 각각 만듭니다.
  • 단, 대사를 두 벌로 관리하면 비교 결과가 텍스트 차이로 오염됩니다.
  • 무엇을 말하는가(story_*)는 양쪽이 같이 읽습니다.
  • 어떻게 보여주는가(present_*)만 빌드별로 갈랐습니다.

두 빌드 대조 — 무엇이 같고 무엇이 다른가

채팅 빌드영상 빌드
흐름 데이터 story_node — 동일 파일 공유
대사 데이터story_dialogue 불필요 (클립에 포함)
연출 파일없음 — 씬별 차등이 없어 클라 상수 present_video
읽는 파일 수2개2개
대사 표현말풍선 순차 출력 클립 재생 + 자막
진행 속도사용자가 탭으로 조절 클립 길이로 고정
스틸컷말풍선 사이에 삽입 클립 안에 녹임 (노드 건너뜀)
필요 에셋초상화 · 표정 10종 · 스틸컷 2장 씬 클립 4개 · 합계 55초
태스크 진입 동일 — task 노드에서 머지보드로

영상 빌드는 두 가지 안 — 제작 방식을 먼저 정해야 합니다

  • 같은 “영상 빌드”라도 만드는 방식이 둘로 갈립니다. 클립 개수·길이·제작 기간이 전부 달라집니다.
  • 데이터는 양쪽 다 동일합니다 — present_video의 clip이 무엇을 가리키느냐만 바뀝니다.
A. 스틸컷 이어붙이기 B. 풀스크린 애니메이션
강점
  • 제작 기간·비용이 짧고 낮음
  • 컷 단위라 부분 수정이 쉬움
  • 대사가 바뀌면 해당 컷만 교체
  • 스틸컷 에셋을 채팅 빌드와 공유 가능
  • 몰입도가 가장 높음
  • 카메라·모션·사운드까지 연출 자유도가 큼
  • 채팅과의 차이가 가장 뚜렷해 비교 대비가 선명함
약점
  • 정지 컷 전환이라 연출 폭이 제한됨
  • 대사가 길면 단조로워짐
  • 영상다움이 약해 채팅과의 차이가 덜 드러날 수 있음
  • 제작비·기간 부담이 큼
  • 수정하려면 다시 뽑아야 함
  • 퀄리티 편차가 비교 결과에 섞일 수 있음

④ 퀘스트 플로우 씬 ID가 바뀌는 자리에 게임플레이가 낀다

  • 씬 ID는 {일차}_{태스크번호}_{begin|end} 형식입니다.
  • begin = 태스크 수락 전 대사, end = 완료 후 대사.
  • 대사 사이에 끼는 게 태스크인지 스틸컷인지는 node_type으로 전부 구분해 두었습니다. 추측할 부분이 없습니다.
  • 대사 본문은 이 문서에 싣지 않았습니다. story_dialogue.json의 text_en에 그대로 있습니다.
