PROTO-001 스토리 연출 채팅 영상 내부 테스트 2026. 8. 14.

채팅 vs 영상, 같은 스토리로 붙여보기

스토리 전달 방식을 채팅 화면과 영상 화면 중 무엇으로 갈지 결정하기 위한 3퀘스트 분량 프로토타입 사양입니다. 빌드는 두 벌로 나누되 스토리 데이터는 한 벌만 공유합니다.

① 작업 목록 프로토 빌드까지 남은 액션

파트항목내용세부
클라채팅 빌드story_node + story_dialogue 2개만. task 노드에서 머지보드 진입.데이터 →
클라영상 빌드story_node + present_video 2개만. dialogue 노드는 씬 클립 재생으로 대체.데이터 →
아트영상 클립 4개vo_<scene_id>.mp4. 제작 방식(스틸컷 이어붙이기 / 풀스크린) 먼저 결정. 각 씬의 line_count가 담아야 할 대사 줄 수입니다.두 가지 안 →
아트표정 리소스 10종anim_<emotion> 이름으로 전달하면 데이터는 수정 없이 그대로 붙습니다.규격 →
아트스틸컷 2장 선택still_<내용>.png. 채팅 빌드용. 생략 가능하지만 정확한 비교를 위해선 권장 — 영상은 클립에 녹여서 나갑니다.플로우 →
기획duration_sec 기입클립 제작 후 present_video.json에 실제 길이 입력. 현재 0.데이터 →
기획설문 준비6문항. 인원 절반은 채팅 먼저, 절반은 영상 먼저 배정.문항 →

② 설계 원칙 빌드는 두 벌, 콘텐츠는 한 벌

  • 채팅 전용 빌드와 영상 전용 빌드를 각각 만듭니다.
  • 단, 대사를 두 벌로 관리하면 비교 결과가 텍스트 차이로 오염됩니다.
  • 무엇을 말하는가(story_*)는 양쪽이 같이 읽습니다.
  • 어떻게 보여주는가(present_*)만 빌드별로 갈랐습니다.

형식 규약 — PST · PBM과 동일

  • 파일 1개 = 플랫 레코드 배열. 중첩 오브젝트도, 래퍼도 없습니다. 한 파일이 한 종류의 행만 담습니다.
  • 규약을 따르되 파일을 쪼개지는 않았습니다. 퀘스트·태스크·스틸컷은 성격이 달라도 결국 “순서대로 실행되는 노드”라 story_node 한 표에 넣었습니다.
  • 대사도 마찬가지로 조인 없이 한 행에서 끝나게 폈습니다 — 말풍선 방향·리소스 키·텍스트가 전부 story_dialogue 행에 있습니다. 프로토 한정 결정입니다 (아래 참고).
  • key_number가 고유키 — 카테고리별 대역 21xxxx~29xxxx.
  • 빈칸 없음. 문자 해당없음 = none, 수치 해당없음 = 0. 불리언 플래그는 0/1, 사용 여부는 in_use.
  • 배열·상속 없음. 클라가 보는 값은 행마다 전부 채워 두었습니다 (연출 defaults 상속을 없애고 씬마다 실값을 씀).

두 빌드 대조 — 무엇이 같고 무엇이 다른가

채팅 빌드영상 빌드
흐름 데이터 story_node — 동일 파일 공유
대사 데이터story_dialogue 불필요 (클립에 포함)
연출 파일없음 — 씬별 차등이 없어 클라 상수 present_video
읽는 파일 수2개2개
대사 표현말풍선 순차 출력 클립 재생 + 자막
진행 속도사용자가 탭으로 조절 클립 길이로 고정
스틸컷말풍선 사이에 삽입 클립 안에 녹임 (노드 건너뜀)
필요 에셋초상화 · 표정 10종 · 스틸컷 2장 씬 클립 4개
태스크 진입 동일 — task 노드에서 머지보드로

영상 빌드는 두 가지 안 — 제작 방식을 먼저 정해야 합니다

  • 같은 “영상 빌드”라도 만드는 방식이 둘로 갈립니다. 클립 개수·길이·제작 기간이 전부 달라집니다.
  • 데이터는 양쪽 다 동일합니다 — present_video의 clip이 무엇을 가리키느냐만 바뀝니다.

프로토에서는 A로 가는 쪽을 권합니다. 이번에 답하려는 질문은 “영상 퀄리티가 어느 정도여야 하나”가 아니라 “채팅이냐 영상이냐”입니다. B로 만들면 퀄리티 차이가 비교를 덮어버립니다. A만으로도 화면이 넘어간다는 경험은 그대로 검증됩니다.

③ 퀘스트 플로우 씬 ID가 바뀌는 자리에 게임플레이가 낀다

  • 씬 ID는 {일차}_{태스크번호}_{begin|end} 형식입니다.
  • begin = 태스크 수락 전 대사, end = 완료 후 대사.
  • 대사 사이에 끼는 게 태스크인지 스틸컷인지는 node_type으로 전부 구분해 두었습니다. 추측할 부분이 없습니다.
  • 대사 본문은 이 문서에 싣지 않았습니다. story_dialogue.json의 text_en에 그대로 있습니다.

// 채팅 빌드 — 파일 2개
for n in story_node                       // node_order 순 = 실행 순서
    if n.node_type = "dialogue"
        lines = story_dialogue where scene_id = n.scene_id and part = n.part
        for l in lines                    // step 순
            drawBubble(l.text_en, l.direction, l.anim)
    if n.node_type = "task"      openMergeBoard(n.task_ref)

story_node — 11행 · 실행 순서 그 자체

필드타입설명
key_numberint고유키. 21xxxx 대역.
node_orderint전역 실행 순서. 1부터 11까지 이 순서대로만 처리하면 됩니다.
quest_idstring묶음 키. 실행 순서는 node_order가 결정합니다.
quest_orderint퀘스트 순서. 태스크 팝업·진행바에 노출됩니다.
task_dayint일차. 팝업 하단 Day N 표기용. 튜토리얼은 0.
node_typeenumdialogue · task · stillcut.
scene_id · partstring · intdialogue 행에만. 이 두 값으로 story_dialogue와 조인합니다. 그 외 none · 0.
node_idstringtask·stillcut 행에만. 그 외 none.
labelstring팝업에 뜨는 태스크 이름(예: Something Fishy). task·stillcut 행에만.
portraitstring팝업 좌측 캐릭터 아이콘. task 행에만.
gimmickenumdecorate · merge. task 행에만. edit_pos가 있으면 decorate입니다.
edit_posstring꾸미기가 놓이는 좌표. 없으면 none.
task_ref · task_coststring · int태스크 코드와 에너지 소모. 팝업 Start 버튼 숫자가 task_cost입니다.
reward_1_item · reward_1_amountstring · int팝업 Rewards 칸. 없으면 none · 0.
assetstringstillcut 행의 이미지 파일명. 그 외 none.
origin_scene · origin_stepstring · int씬 중간에 삽입된 노드가 원본의 어느 행을 대체했는지. 씬 뒤에 붙는 노드는 none · 0.

story_dialogue — 35행 · 대사 한 줄 = 한 행

필드타입설명
scene_id · partstring · intstory_node의 dialogue 행과 이 두 값으로 조인합니다. 이게 유일한 조인입니다.
stepint씬 안에서의 순서. 연속이 아닙니다 — 삽입 노드가 가져간 번호는 빠집니다.
speakerstring화자명. 표시용이자 초상화 선택 키.
direction1 | 2말풍선 위치. 1 = 화면 좌측, 2 = 우측.
emotionstring표정 키. 10종.
animstring플레이스홀더 리소스 키. 아트 확정 시 이 열을 교체합니다.
text_enstring대사 본문(영문).

anim은 리매핑 대상이 아니라 아트에 요구하는 파일명입니다. 이 값에 맞춰 파일을 받으면 데이터를 고칠 일이 없습니다 → ⑤ 에셋 규격. text_en만 프로토 한정 인라인입니다 — 다국어가 붙으면 string_code + 문자열 테이블로 다시 분리하는 게 맞습니다.

present_video — 4행 · 영상 빌드 전용

필드타입설명
