상한을 정하는 건 틱톡임

  • 퍼블마 전면광고 실패의 90.6%가 Interstitial ad frequency limits reached 계열임. 클라가 30초로 막고 있는데도 이만큼 걸림
  • 성공한 노출끼리의 최소 간격이 코지 41초·퍼블마 49초(하위 5% 기준)임. 30초 미만으로 붙는 노출은 양쪽 다 0.1% 미만
  • 쿨다운이 없는 코지와 30초인 퍼블마를 대조하면, 판당 시도를 30% 더 넣었을 때 판당 노출은 9%만 늘었음 — 시도 증가분의 30%만 노출로 전환됨
  • 이 30%는 구좌를 늘려 시도를 넣었을 때의 값임. 쿨다운만 풀어서 같은 구좌를 더 자주 두드리는 건 전환율이 0에 가까움 — 틱톡이 거절하던 자리를 다시 두드리는 것이라서. 아래 빨강 상자가 그 경우임

쿨다운을 없애도 노출은 안 늘어남. 코지는 이미 무효라 바꿀 게 없고, 퍼블마는 이 플래그를 제거하면 시도만 늘고 노출은 제자리임(재생값 기준 시도 2.86→3.37 · 노출 1.78 유지). 쿨다운 · 세션 시작 · RV 후 블록은 같은 플래그 하나라 이 결과가 셋 모두에 해당함. 노출을 실제로 만드는 건 유예 해제와 판 종료 구좌 둘이고, 축별 기여는 5장에 있음.

지금은 광고끼리 안 붙어 있음

확대 전 상태에서 직전 노출로부터 40초 안에 들어온 시도가 코지 8.0% · 퍼블마 1.5~3.0%뿐임. 시도 사이 간격의 중앙값이 코지 판 진입 160초 · 재도전 459초, 퍼블마 판 진입 326초 · 판 종료 285초임.

  • 그래서 지금의 낮은 fill은 우리 구좌가 서로 붙어서 생긴 게 아님 — 틱톡 쪽 빈도 계산에서 이미 거절되고 있는 것임
  • 바꿔 말하면 간격 파라미터는 지금 아무 일도 안 하고 있음. 확대 후에야 광고끼리 붙기 시작하므로, 간격 값은 확대와 한 세트로 정해야 함

문제 — 광고를 켜 둔 채로 절반 이상이 못 봄

틱톡 유저는 가입 첫날에 코지 5.74판, 퍼블마 5.58판을 놂. 그런데 코지 유저의 54%, 퍼블마 유저의 70%가 전면광고를 한 번도 못 봄. 신규 배려 구간(코지 누적 클리어 3판 미만, 퍼블마 첫 4승)이 첫날 판수의 40%를 통째로 막고 있어서임.

두 번째는 구좌임. 코지는 판에 들어갈 때만 붙고 판이 끝나는 시점엔 사실상 구좌가 없음(result_lobby 두 달 59건). 퍼블마는 판 종료 구좌가 이미 있는데 결과창 버튼을 눌러야 발화해서 경로의 일부만 덮음.

고칠 부분 — 두 가지

  • 신규 배려 구간 해제 — 첫 판을 끝낸 시점부터 광고 대상으로 봄
  • 판 종료 구좌 신설 — 결과창에 들어가는 시점에 광고를 붙임

세션 시작 블록·RV 시청 후 블록도 같이 해제함. 플레이 중 N매치마다 노출하는 안은 넣지 않음 — 판 경계에서만 붙임.

두 계산이 겹치는 구간을 KPI로 씀. 코지는 두 값이 1.95와 1.97로 거의 붙었고, 퍼블마는 1.62~2.03으로 벌어짐.

이 작업의 위치 — 보상형 광고로 가기 전 단계

틱톡 측 회신 기준으로 틱톡 미니게임 수익의 중심은 보상형 광고임. 탑 30 게임 대부분이 보상형으로 첫날 광고 매출을 만들고, 틱톡 수익화 문서도 같은 방향을 권함. 전면광고는 전체 게임 매출에서 5% 미만임.

그런데 두 게임의 현재 빌드에 보상형 구좌를 새로 심는 건 사이클이 큼. 그래서 이미 배선돼 있는 전면광고를 먼저 상한까지 열어 보고, 거기서 나온 노출 한계와 이탈 반응을 보상형 논의의 입력으로 씀. 순서는 전면광고 확대 → 실측 → 보상형 설계임.

  • 배선 빌드를 먼저 올림. 세 값을 현행과 같게 둔 채 파라미터가 라이브에서 읽히는지만 확인함 — 값을 넣기 전과 후의 노출이 같아야 배선이 맞은 것임
  • 확인되면 값만 바꿔서 확대함. 되돌리기가 값 원복 한 건으로 끝남
  • 순서가 뒤집혀도 무해함. 값을 먼저 올려도 읽는 코드가 없어 아무 일도 안 일어나고, 배선 빌드만 나간 상태도 기본값이라 현행 동작임
  • 배선과 값을 같은 빌드에 넣지 않음 — fill이 무너져도 되돌리는 데 빌드 한 사이클이 통째로 듦

코지 중앙 래퍼 신설

퍼블마는 ADPlayer.tryShowInterstitialAD가 모든 호출을 한 번 받아서 FTUE 가드를 거기서 걺. 코지에는 이 래퍼가 없어서 화면마다 BasePlatform.instance.tryShowInterstitialAD를 직접 부름 — stage_start 하나만 호출지점이 17곳임(DataManager 13 · 친구/리더보드/토너먼트/프로필 4). 호출지점마다 조건을 넣으면 반드시 빠짐.

  • 코지에 ADPlayer 상당물을 신설하고, 네 파라미터 판정을 전부 거기 한 곳에 둠. 각 화면은 구좌 이름만 넘김. tiktok_it_enabled=0 검사는 이 래퍼 맨 앞에 두어 로그도 남기지 않고 즉시 반환함
  • 17곳 중 다수는 틱톡에서 이미 죽어 있음 — getRecommendedMatchInfo()가 페이스북이 아니면 null을 반환해서 친구·토너먼트 분기가 통째로 안 탐. 래퍼로 모으면 이런 판별이 필요 없어짐
  • 기존 Fbi.tryShowInterstitialAD 직접 호출은 래퍼로 옮길 것. 단 PopupShowCheck의 키보드 치트 1곳은 의도적 예외로 그대로 둠 — 개발용이라 파라미터를 안 타는 게 맞음. 대신 이걸로 확대 동작을 검증하면 안 된다는 걸 QA 주의사항에 적어 둠

클라 상태 모델

파라미터가 만드는 상태는 넷임. 클라가 들고 있어야 하는 값은 lastImpressionAt 하나뿐임.

상태빠져나가는 조건그때 저장·갱신하는 값
전체 정지tiktok_it_enabled=1로 바뀜 (다음 부팅부터)없음 — 광고 호출 자체를 안 함
유예 중클리어 카운터 ≥ tiktok_it_ftue_free_count없음 — 기존 카운터를 읽기만 함

간격 대기 중lastImpressionAt + tiktok_it_min_interval_sec 경과없음
  • 타이머 기준은 4010(노출 성공)임. 4000(시도)이 아님
  • 틱톡이 거절해도(4020) 타이머를 갱신하지 않음. 갱신하면 거절 한 번이 뒤따르는 정상 구좌까지 막아 노출이 오히려 줄어듦
  • lastImpressionAt은 메모리에만 둠. 부팅하면 리셋됨 — 영속 저장하지 않음. 첫 판 진입 전에는 어차피 구좌가 없어서 부작용이 없고, 저장하면 기기 시간 조작이 변수로 들어옴

구좌별 파라미터를 따로 두지 않는 이유

구좌는 아홉인데 파라미터는 넷임. 이 건이 새로 만드는 노출은 판 종료 구좌 하나뿐이고, 나머지 구좌는 노출이 새로 생기는 게 아니라 대상 유저가 늘어나는 것이라 유예 값 하나가 그대로 레버가 됨.

재도전 구좌를 따로 끄는 값은 두지 않음. 이 건이 재도전 노출을 새로 만든 게 아니라서, 되돌릴 일이 생기면 유예 값을 올리는 것으로 같은 유저층이 그대로 빠짐. 그래도 부족하면 그때 tiktok_it_slot_retry를 추가하면 되고, 지금 미리 만들면 QA 조합만 늘어남.

세션 시작 블록과 RV 시청 후 블록은 파라미터를 주지 않고 제거함. 실측에서 이 둘의 노출 기여가 0%p였고(시도만 2.86→3.37로 늘고 노출은 1.78 그대로), 코지는 이미 코드상 무효라 게임 간 동작도 이걸로 통일됨. 조이는 수단은 tiktok_it_min_interval_sec 하나로 충분함.

tiktok_it_enabled는 되돌리기용이 아니라 끄기용임. 세 축을 현행값으로 되돌리는 것과 전면광고를 통째로 내리는 것은 다른 상태인데, 지금까지 스펙엔 후자가 없었음. 틱톡 쪽 정책 이슈·광고 SDK 장애·예상 밖 이탈처럼 원인을 파악하기 전에 일단 멈춰야 하는 상황에서 값 하나만 내리면 되게 둠. 세 값을 동시에 정확히 되돌리는 것보다 사고 시 실수가 적음.

퍼블마도 같이 넣음. 퍼블마는 전면광고를 끌 수단이 클라 상수뿐이라 지금은 빌드를 다시 올려야 함. 두 게임이 같은 이름·같은 동작으로 갖고 있어야 사고 때 한 사람이 둘 다 내릴 수 있음.

범위 밖은 클램프하지 않고 기본값으로 떨어뜨림. 형변환이 안 되는 값(문자열·null·소수)도 같음. 잘못 넣은 값이 조용히 옆 값으로 바뀌면 시트를 봐도 실제 동작을 알 수 없음.

네 값 모두 tiktok_ 접두사를 붙임 — 퍼블마 const 탭과 코지 CDN 폴더는 다른 플랫폼 빌드도 같이 보는 자리라, 이름만 보고 이 값이 틱톡에만 먹는다는 걸 알 수 있어야 함.

tiktok_it_min_interval_sec은 0 · 5 · 30 · 40 네 값만, tiktok_it_ftue_free_count는 0 · 1 · 3 · 4만 씀. 임의값을 넣지 않기로 하면 QA가 확인할 조합이 고정됨.

일일 상한은 넣지 않음. 날짜 기준이 두 게임이 다르고(퍼블마는 UTC, 코지 checkDateChanged는 기기 로컬 자정) 리셋·시간 조작까지 QA 범위가 커짐. 조이는 건 tiktok_it_min_interval_sec을 40으로 올리는 것으로 충분함.

계측

  • 기존 4000 / 4010 / 4020 그대로 씀. 판 종료 구좌는 type에 코지 stage_end, 퍼블마 game_over_enter로 신규 값을 넣어 기존 game_over(버튼 클릭)와 구분함
  • type은 4000·4010·4020 셋 모두에 같은 값으로 실을 것. 구좌별 fill = 같은 type의 4010 ÷ 4000인데, 4020에 type이 없으면 어느 구좌가 거절당했는지를 못 봄 — 판정 기준이 구좌별 fill이라 이게 빠지면 판정 자체가 안 됨. 조회할 땐 구버전 호환으로 coalesce(data.type, data.position)을 쓸 것
  • 4000의 data에 그 시점 적용값을 같이 실을 것 — 네 값을 이어붙인 짧은 문자열 하나면 됨(예: 1-1-1-5). 반영이 다음 세션부터라 롤아웃 이행 구간에는 한 시각에 신·구 유저가 섞이는데, 시트 변경이력은 창 경계만 줄 뿐 유저를 신/구로 가르지 못함. 클라가 이미 들고 있는 값이라 서버 왕복이 필요 없음
  • tiktok_it_enabled=0이면 광고 이벤트가 아예 안 찍혀서 정책상 끈 것과 광고 SDK 장애가 로그에서 구분되지 않음. 세션당 1회 설정 상태 로그를 광고 이벤트와 별개로 남길 것
  • 코지 4020의 error_message가 지금 [object Object]로 올라감 — 8월 실패 2,406건의 95.3%임. 퍼블마처럼 문자열로 직렬화할 것. 이걸 고쳐야 확대 후 fill이 떨어졌을 때 틱톡 빈도 제한인지 인벤토리 부족인지 구분됨
  • 파라미터 변경일은 시트 변경이력에 남김. 전후 비교의 창 경계가 이 기록에서 나옴

추가로 확인할 것 둘. 파라미터를 못 받았을 때(JSON 삭제·네트워크 차단)는 현행 동작으로 떨어져야 함. 정해진 값 밖의 수를 넣었을 때(예: 간격 999)는 기본값으로 떨어지고 크래시가 없어야 함.

키보드 치트로 확대 동작을 검증하지 말 것. 코지 PopupShowCheck의 num1 치트는 Fbi.tryShowInterstitialAD를 직접 부름 — 틱톡 플랫폼 분기도, 새 파라미터도 안 탐. 여기서 광고가 뜨는 건 아무것도 증명하지 않음. 확인은 반드시 실제 판 흐름으로 할 것.

코지는 차단 지점이 두 곳임(5장). 한 곳만 고치면 값을 바꿔도 노출이 안 늘어남 — 그래서 시트 값만 보지 말고 첫 판 종료 결과창을 실기로 확인할 것.

판정

  • 첫 지표는 fill임. 예측이 코지 28% · 퍼블마 36~45%이므로 임계는 그 아래인 코지 24% · 퍼블마 32%로 둠. 예측대로 떨어지는 건 성공이지 롤백 사유가 아님 — 임계를 예측치에 붙여 놓으면 성공 시나리오가 곧장 조임 트리거를 밟음
  • fill은 전체가 아니라 구좌별로 볼 것. 확대 전에도 코지 재도전 구좌가 37.7%로 이미 최저임 — 전체 평균만 보면 이 구좌가 먼저 무너지는 걸 놓침. 판 종료 구좌를 켜면 재도전 광고가 바로 뒤에 붙으므로 여기가 가장 먼저 반응함
  • 수익은 노출 수로 봄. 시도는 처치가 걸렸는지 확인하는 용도지 성과 지표가 아님
  • 이탈은 첫날 판수 · 첫날 세션 수 · D1 리텐션으로 봄(판수=2100_GAMEPLAY_START · 코호트=가입일 · 개발계정 제외 · 시각축 UTC). 전량 적용이라 홀드아웃이 없으므로 전후 비교임 — 배포일을 기록하고 부분일과 롤아웃 중간일을 뺄 것
  • 틱톡 월 유저가 코지 2,300명 수준이라 ±10% 미만 변화는 검출되지 않음. 작은 차이를 두고 판정하지 말 것
  • 축이 나뉘어 있으므로 되돌릴 때 게임별로 다른 걸 끔. 노출 기여가 퍼블마는 유예 해제, 코지는 판 종료 구좌 쪽이 큼 — 이탈이 났다고 양쪽을 같이 끄지 말 것
  • 보상형 논의로 넘기는 산출물: 전면광고 노출의 실측 천장(유저당 몇 회에서 더 안 늘어나는지) · 그 지점에서의 첫날 판수·D1 변화. 이 둘이 보상형 구좌를 몇 개, 어디에 넣을지의 근거가 됨

퍼블마 const_B 탭은 손대지 않았음. 값이 const와 다른 걸로 보아 실험용 B군 세트로 보이는데, 이게 지금 살아 있는지 확인이 안 됨. 살아 있다면 B군 유저는 네 값을 못 받아 기본값(현행)으로 떨어져서 확대가 A군에만 걸림. 배포 전에 const_B가 실제로 쓰이는지 확인하고, 쓰인다면 같은 4행을 그쪽에도 넣을 것.

코지 CDN 업로드 파일

cozy-tiles/data/tiktok_ad_config.json — 확대 적용값. 올린 뒤 CDN 무효화를 반드시 할 것.

{
  "tiktok_it_enabled": 1,
  "tiktok_it_ftue_free_count": 1,
  "tiktok_it_slot_stage_end": 1,
  "tiktok_it_min_interval_sec": 5
}

배선 빌드 검증용 — 현행과 똑같이 도는 값. 이걸 올린 상태에서 노출이 안 변해야 배선이 맞은 것임.

{
  "tiktok_it_enabled": 1,
  "tiktok_it_ftue_free_count": 3,
  "tiktok_it_slot_stage_end": 0,
  "tiktok_it_min_interval_sec": 0
}
