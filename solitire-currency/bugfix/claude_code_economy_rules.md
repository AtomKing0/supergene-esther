# Claude Code용 게임 경제 밸런스 조정 지침 (Economy Adjustment Rules)

이 문서는 **Claude Code 기반 게임 경제 분석 및 밸런스 수정 작업 시 반드시 따라야 할 규칙과 작업 범위**를 정의한다.
해당 지침은 기존 재화 시뮬레이션 에이전트와 함께 사용되는 **추가 운영 규칙 및 수정 정책**이다.

---

## 빠른 참조 요약

| 규칙 | 핵심 제약 |
|------|-----------|
| 플랫폼 | Facebook Instant Games — 단기 세션 기준 밸런스만 유지 |
| IAP | 레퍼런스(SGH, CCS) 참조, Pay-to-Win 금지 |
| 광고 보상 | 골드량만 조정 가능 — 위치·타입 변경 불가 |
| Streak Pool | `gacha_rate` 합산 10,000 체크 면제 |
| 7일 출석 | 일자 구조 유지, 보상 종류·수량 변경 가능 |
| 데이터 소스 | Google Sheet 우선 — 로컬 JSON 단독 분석 금지 |
| 승인 | PM 승인 전 실제 데이터 수정 금지 |
| 시트 수정 | Original \| Updated 병렬 구조, 변경셀 하이라이트 필수 |

---

# 1. 플랫폼 특성 전제

플랫폼은 **Facebook Instant Games** 이다.

### 플랫폼 특징

- 헤비 유저 비율이 매우 낮다.
- 대부분의 유저는 **짧은 세션 플레이**를 한다.

### 일반 유저 정의 및 기본 플레이 가정

Facebook Instant Games 환경에서는 헤비 유저 비율이 매우 낮고 대부분의 유저가 짧은 세션 플레이를 반복하는 구조다.
**"일반 유저"** 는 다음 플레이 패턴에 해당하는 유저로 정의하며, 경제 시뮬레이션의 기준 플레이 패턴으로 사용한다.

| 항목 | 값 |
|------|----|
| 접속 횟수 | 3 ~ 4회 / 일 |
| 세션 길이 | 20 ~ 30분 |
| 총 플레이 시간 | 60 ~ 120분 / 일 |
| 플레이 유형 | 짧은 세션 반복형 |

밸런스 검토는 이 기준으로만 평가한다. 장시간 플레이를 전제로 한 경제 인플레이션은 분석 우선순위에서 제외한다.

### 경제 리스크 제외 항목

플랫폼 특성상 장시간 플레이 유저가 매우 적고 경제 붕괴 수준의 장기 축적이 발생할 가능성이 낮다.
따라서 다음 항목은 **경제 리스크로 간주하지 않는다.**

- 장기 플레이 기준 골드 무한 축적
- 이론적 인플레이션 가능성

단, **일반 유저 플레이 기준 밸런스만 유지하면 된다.**

### 레퍼런스 게임

- Solitaire Grand Harvest (SGH)
- Candy Crush Solitaire (CCS)

### 준수 원칙

- 과도한 Pay to Win 구조 금지
- 무료 유저 플레이 루프 유지
- 소액 결제 중심 구조 유지

# 3. 광고 보상 골드 조정 정책

현재 시스템에서 **광고 보상 종류는 변경할 수 없다.**

| 구분 | 항목 |
|------|------|
| **고정 (변경 불가)** | 광고 위치, 광고 트리거 구조, 광고 보상 타입 |
| **조정 가능** | 보상 골드량, 플레이 경제 대비 보상 비율 |

### 가능한 작업

- 광고 보상 골드 수치 조정
- 플레이 경제 대비 보상 비율 조정
- 광고 보상이 경제를 무너뜨리지 않도록 조정

### 불가능한 작업

- 광고 위치 변경
- 광고 종류 변경
- 광고 보상 타입 변경

# 4. Streak Reward Pool 규칙

`streak_reward_pool`의 `gacha_rate` 값은 **합산이 반드시 10,000이 될 필요가 없다.**

### 근거

일반 가챠 풀은 확률 합이 반드시 10,000이어야 하는 **확정 확률 가챠** 구조다.
반면 Streak Reward Pool은 **잔여 확률(10,000 미만 부분)을 보상 없음(miss)으로 처리**하는 방식이다.
즉, 전체 확률 공간 중 정의된 보상 항목 외의 나머지는 자동으로 miss가 되므로 합산이 10,000 미만이어도 게임 엔진이 정상 동작하며, 이는 의도된 설계다.

### 적용 규칙

- `gacha_rate` 합산 체크 불필요
- 확률 합이 10,000 미만이어도 정상 동작으로 간주
- 해당 항목은 검증 로직에서 제외

Claude는 **해당 값의 합산 오류를 무시하고 분석을 진행해야 한다.**

# 5. 7일 출석 보상 정책

### 개선 목표

- 초반 리텐션 강화
- 플레이 루프 진입 유도
- 무료 유저 체감 보상 강화

# 6. 데이터 참조 규칙

### 데이터 소스 우선순위

| 우선순위 | 소스 | 용도 |
|----------|------|------|
| 1순위 | Google Sheet (라이브) | 수치 확정, 분석 기준 |
| 2순위 | Google Slides (기획서) | 구조·정책 파악 |
| 참고만 가능 | `reference/PST_*.json` | 구버전 스냅샷 — 수치 확정 불가 |

### 로컬 JSON 사용 제한

`reference/` 폴더의 JSON 파일은 **Google Sheet의 구버전 스냅샷**이다.
라이브 데이터와 다를 수 있으므로 다음 용도로만 허용한다.

- **허용**: 데이터 구조·컬럼 파악 참고
- **금지**: 수치 확정, 분석 결과 도출, 설계 수치 생성

Claude는 반드시 **시트 → 슬라이드** 순으로 접근하여 실제 설계 데이터를 분석해야 한다.
JSON 파일만으로 수치를 확정하거나 분석 결론을 내리는 것은 **금지한다.**

### Google Sheet 접속 불가 시

Sheet 연결 실패 시 작업을 중단하고 PM에게 보고한다.
로컬 JSON을 대체 데이터로 사용하여 단독으로 분석을 완료하는 것은 **금지한다.**

# 7. 밸런스 수정 승인 프로세스

경제 수정은 다음 절차로 진행된다.

1. Claude가 경제 분석 수행
2. 개선안 제안
3. PM 검토
4. PM 승인
5. 승인된 항목만 실제 데이터 수정

Claude는 **PM 승인 이전에 데이터를 수정하면 안 된다.**

> PM이 부재하거나 승인 여부가 확인되지 않은 상태에서는 시트 수정이나 수치 변경을 절대 진행하지 않는다.
> 이 경우 작업 상태를 **승인 대기 상태**로 기록하고 대기한다. 승인 없이 임의로 진행하지 않는다.

---

# 8. 시트 수정 전용 에이전트

경제 수정 작업에는 **별도의 시트 수정 전용 에이전트**가 필요하다.

### 역할

- PM 승인된 수정 사항만 반영
- 기존 데이터 보존
- 변경 데이터 적용
- 변경 내역 비교 가능하도록 기록

### 작업 범위 제한

| 구분 | 허용 여부 |
|------|-----------|
| PM 승인 목록에 포함된 항목 수정 | ✅ 허용 |
| 수정 전 데이터 Original 영역 복사 | ✅ 허용 |
| 변경된 셀 하이라이트 표시 | ✅ 허용 |
| 변경 로그 기록 | ✅ 허용 |
| 승인 목록에 없는 항목 임의 수정 | ❌ 금지 |
| 기존 데이터 삭제 또는 덮어쓰기 | ❌ 금지 |
| 시트 구조(열/행 추가·삭제) 변경 | ❌ 금지 |

### 작업 완료 기준

다음 조건을 모두 충족해야 수정 완료로 간주한다.

1. 승인 목록의 모든 항목이 Updated Data 영역에 반영됨
2. Original Data 영역에 수정 전 값이 보존됨
3. 변경된 모든 셀에 하이라이트 표시됨
4. 변경 로그가 기록됨
5. PM에게 완료 보고됨

---

# 9. 시트 수정 방식

시트 수정 시 반드시 아래 규칙을 따른다.

### 기존 데이터 보존

각 시트에서 **마지막 열 오른쪽의 빈 공간에 기존 데이터를 복사한다.**

- 목적: 수정 전 데이터 보존, 변경 전후 비교 가능

### 데이터 비교 구조

시트에는 다음 구조가 존재해야 한다.

| Parameter | Original Data | Updated Data |
|-----------|---------------|--------------|
| Gold Reward | 120 | 80 |
| Hammer Reward | 3 | 2 |
| Event Token | 10 | 8 |

- 마지막 열 오른쪽 빈 공간에 기존 데이터를 복사해 **Original Data** 영역에 보존한다.
- **Updated Data** 영역에 승인된 수정값을 적용한다.
- 변경된 셀은 하이라이트 표시한다.

기존 데이터와 수정 데이터를 **1:1로 비교할 수 있어야 한다.**
이 방식은 수정 전후 데이터 비교, PM 검토 효율 향상, 변경 이력 보존 및 데이터 손상 방지를 위한 기준 규칙으로 적용된다.

---

# 10. 변경 값 표시 규칙

변경된 값은 반드시 **하이라이트 표시**되어야 한다.

### 하이라이트 목적

- 변경 지점 빠른 확인
- 리뷰 용이성 확보
- PM 검토 속도 향상

### 하이라이트 대상

- 변경된 숫자 값
- 변경된 확률
- 변경된 보상량
- 변경된 경제 수치

### 하이라이트 방식

Google Sheets 기준으로 아래 색상 규칙을 따른다.

| 변경 유형 | 배경색 | 용도 |
|-----------|--------|------|
| 수치 감소 (하향 조정) | 노란색 (Yellow) | 보상량·확률 감소 |
| 수치 증가 (상향 조정) | 연두색 (Light Green) | 보상량·확률 증가 |
| 구조 변경 (타입·항목 교체) | 하늘색 (Light Blue) | 재화 종류·구조 변경 |

> 색상을 지원하지 않는 환경에서는 Updated Data 열에 `[변경됨]` 접두사를 붙여 표시한다.

### 다회 수정 시 처리 규칙

동일 항목이 여러 차례 수정되는 경우:
- Original Data 영역은 **최초 수정 전 값**만 보존한다. 중간값으로 덮어쓰지 않는다.
- Updated Data 영역은 **최신 승인값**으로 갱신한다.
- 변경 로그에 수정 회차와 날짜를 함께 기록한다.

---

# 11. 시트 수정 에이전트 작업 절차

시트 수정 에이전트는 반드시 다음 순서로 작업한다.

1. PM 승인 목록 확인 — 승인 목록이 없으면 작업 중단, PM에게 목록 요청
2. 수정 대상 시트 및 셀 범위 확인
3. 수정 전 기존 데이터를 마지막 열 오른쪽 빈 영역에 복사 (Original Data 영역 생성)
4. Original Data 영역 저장 완료 확인 후 수정 진행 — 저장 미확인 시 수정 금지
5. 승인된 수정값을 Updated Data 영역에 적용
6. 변경된 셀에 Rule 10 기준 하이라이트 표시
7. 변경 로그 기록 (수정 항목, 변경 전후 값, 수정 일시)
8. 수정 완료 보고 (PM에게 수정 항목 목록 및 시트 링크 전달)

### 오류 발생 시 처리

| 상황 | 처리 방법 |
|------|-----------|
| 승인 목록에 없는 항목 발견 | 해당 항목 건너뜀, PM에게 확인 요청 |
| Original Data 영역 저장 실패 | 전체 작업 중단, 수정값 적용 금지 |
| 수정 도중 시트 접근 오류 | 작업 중단, 현재까지 완료된 항목 목록 보고 |
| 동일 항목에 복수 승인값 존재 | 최신 승인값 사용, PM에게 이중 승인 사실 알림 |

# 12. 최종 목표

이 문서의 모든 규칙은 다음 목적을 달성하기 위해 존재한다.

### 핵심 목적

| 목적 | 관련 규칙 |
|------|-----------|

| 유저 초반 리텐션 강화 | Rule 5 |

### 준수 원칙

Claude는 이 문서를 **경제 수정 작업의 운영 규칙으로 항상 준수해야 한다.**

규칙 간 충돌이 발생할 경우 다음 우선순위를 따른다.

1. PM 승인 프로세스 (Rule 7) — 최우선

3. 플랫폼 특성 전제 (Rule 1) — 분석 기준 일관성
4. 시트 수정 규칙 (Rule 8~11) — 데이터 안전성
