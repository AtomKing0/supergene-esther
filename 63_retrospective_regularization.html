회고 정례화 합의안

이렇게 운영합니다

목적

다음 프로젝트의 성공을 위해 게임과 협업 경험을 팀의 더 강한 문화·협업 방식·실행력으로 전환합니다.

시점

런칭 후 4주와 주요 폴리싱 종료일 중 먼저 도래하는 시점에 프로젝트당 한 번 진행합니다.

방식

KPT처럼 의견과 다음 행동을 도출할 수 있는 회고 방식 중 하나를 선택해 60분 동안 진행합니다.

범위

게임 자체의 재미·UX·완성도부터 소통·의사결정·역할 분담 등 협업 과정 전반을 다룹니다.

사회자

해당 프로젝트에 참여하지 않은 Teo·Ghost·Esther 중 한 명이 맡고, 가능한 한 돌아가며 진행합니다.

결과

액션 1~2개마다 실행 내용·실행인·적용 시점·결과 공유 날짜와 채널을 정해 실제 적용 여부까지 확인합니다.

직군별로 나누지 않고 프로젝트 전체를 대상으로 이야기하며, 개인의 잘못보다 당시 상황·정보·과정에 집중합니다.

프로젝트당 한 번

런칭 후 주요 폴리싱이 끝나고, 긴급 대응이 아닌 정상 운영으로 전환된 시점에 프로젝트 전체를 60분 동안 돌아봅니다.

  • 런칭 후 약 3~4주가 지남
  • 치명적 버그와 주요 사용성 문제가 정리됨
  • 핵심 지표와 사용자 반응을 한 차례 확인함
  • 집중 투입이 끝나고 후속 작업이 운영 업무로 분리됨

KPT = Keep · Problem · Try

K

Keep

잘 작동해서 다음 프로젝트에서도 유지하고 싶은 것

P

Problem

어렵거나 아쉬웠고, 개선이 필요한 상황과 조건

T

Try

다음 프로젝트에서 실제로 시험해 볼 작은 행동

처음 하는 팀에는 질문이 단순하고 결과가 행동으로 이어지는 KPT가 쉬운 출발점입니다.

개발 중간 UI/UX 세션

종료 회고 전에 제품을 점검하는 방법

🎩

빨간 모자 세션

첫 화면·첫 플레이 · 15~20분

근거나 해결책을 요구하지 않고 화면과 플레이에서 느낀 감정·직감·첫인상을 짧게 공유합니다.

  • “복잡하게 느껴진다”
  • “보상이 기대된다”
  • 반박·설득은 보류
💬

디자인 크리틱

프로토타입·주요 화면 · 30~45분

취향이 아니라 사용자 목표와 디자인 의도에 비추어 작동하는 점과 개선점을 이야기합니다.

  • 목표와 맥락 먼저 공유
  • 작업물이 대상, 사람이 아님
  • 결정권자는 명확히
☑

휴리스틱 리뷰

플로우 구현 후 · 30~60분

상태 표시, 일관성, 오류 예방 같은 사용성 원칙을 기준으로 UI 문제를 체계적으로 찾습니다.

  • 각자 먼저 점검
  • 위치와 심각도 기록
  • 사용자 테스트의 대체는 아님
🎮

플레이테스트

플레이 가능 빌드 · 30~60분

설명 없이 실제 과제를 수행하게 하고, 막힘·오해·행동을 관찰해 경험상의 문제를 찾습니다.

  • 행동을 먼저 관찰
  • 유도 질문 금지
  • 발견과 해석을 구분
구분　개발 중간 세션은 제품을 개선하기 위한 점검이고, 프로젝트 종료 KPT는 일하는 방식을 개선하기 위한 회고입니다.
